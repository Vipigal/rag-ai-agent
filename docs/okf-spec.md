# Open Knowledge Format (OKF) v0.2

OKF is a minimal format for knowledge that is authored by people,
generated by agents, and read by both: a directory of markdown files with
YAML frontmatter. No schema registry, no central authority, no required
tooling — if you can `cat` a file you can read OKF, and if you can
`git clone` a repo you can ship it.

This repository is one OKF bundle rooted at the repo root. What follows is
the part of the format this bundle actually relies on; the conventions
layered on top of it — which types exist here, where each concept lives,
the approval gate — are in the
[Authoring Guide](/docs/authoring-guide.md).

## 3.1 Reserved filenames

Two filenames have defined meaning at any level and are never concept
documents:

| Filename   | Purpose                     |
| ---------- | --------------------------- |
| `index.md` | Directory listing (§8).     |
| `log.md`   | Update history (§9).        |

Every other `.md` file is a concept document and carries frontmatter.

## 4.1 Frontmatter

`type` is the only always-required key; a concept carrying just `type` is
conformant. Producers may add any other key, and consumers must tolerate
unknown types and unknown fields rather than reject the document.

```yaml
---
type: <Type name>        # REQUIRED — routing, filtering, presentation
title: <display name>
description: <one sentence; index.md entries reuse it verbatim>
tags: [<tag>, <tag>]
# plus the provenance, trust and lifecycle fields below
---
```

## 5.1 Provenance: `sources`

A concept that derives from external or internal material cites it, and
cites it per claim — an inline footnote whose label matches a
`sources[].id`:

```yaml
sources:
  - id: <stable-key>
    resource: <url or bundle-relative path>
    title: <human-readable label>
```

## 5.2 Trust: `generated` and `verified`

`generated` records how the current content was produced; `verified`
records who confirmed it. They are separate because whoever *wrote* a
concept need not be whoever *confirmed* it.

```yaml
generated: { by: <actor>, at: <ISO 8601 UTC> }
verified: { by: <actor>, at: <ISO 8601 UTC> }
```

`generated.at` marks the content's last meaningful change. `verified` is
independent of it: content can change without re-confirmation, and facts
can be re-confirmed without regeneration — so a `generated.at` later than
`verified.at` is the signal that a concept needs re-review. `verified` may
also be a list, when several actors checked independently.

## 5.3 Trust tiers

Derived from `verified`, lowest to highest: no `verified` key ⇒
**unverified**; `verified` by non-`human:` actors only ⇒
**machine-confirmed**; `verified` by a `human:<id>` actor ⇒
**human-reviewed**. Advisory signals, never access control.

## 5.4 Lifecycle: `status`

```yaml
status: stable # draft | stable | deprecated
```

`draft` not yet reviewed, possibly incomplete; `stable` ready for
consumption; `deprecated` kept for links and history, no longer current.
Absent `status` ⇒ `stable`.

## 6.1 Links between concepts

Two forms. **Bundle-relative** links begin with `/` and resolve against
the bundle root — the recommended form, because it survives a document
moving within its subdirectory:

```markdown
See the [system architecture](/docs/architecture.md).
```

**Relative** links are ordinary markdown relative paths (`./other.md`).

A link asserts a relationship; which kind — parent, reference, dependency
— is carried by the surrounding prose, not by the link. Consumers must
tolerate a broken link: a target that does not exist is not malformed, it
may be knowledge not yet written.

## 7. Actor convention

Identity fields (`generated.by`, `verified.by`) use one convention:
`<producer>/<version>` for agents and tools (`claude_code/claude-fable-5`),
`human:<id>` for a person (`human:vinicius`), `process:<id>` for an
automated process. Trust classification keys off the `human:` prefix, so
hand-authored or human-confirmed content must use it.

## 8. Index files

An `index.md` may appear in any directory, including the bundle root. It
enumerates that directory's contents so a reader — human or agent — can
see what exists before opening anything: **progressive disclosure**. Index
files carry no frontmatter, except that a bundle-root `index.md` may carry
`okf_version`. The body is one or more headed sections listing concepts,
each entry reusing the concept's `description`.

## 9. Log files

A `log.md` may appear at any level to record the history of changes to
that scope: a flat list of date-grouped entries, newest first, each marked
`**Creation**`, `**Update**` or `**Deprecation**`.

```markdown
# Directory Update Log

## 2026-05-22

- **Update**: Added a reference for [Customer Metrics](/tables/customer-metrics.md).
- **Creation**: Established the [Dataplex Playbook](/playbooks/dataplex.md).
```
